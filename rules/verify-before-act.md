# Verify before act — проверяй источник, не лезь в память

## Принцип

**Память Claude кривая после 3-5 сообщений. Каждое factual утверждение, каждое действие на файле / в Sheets / в БД / в Git — проверка в реальном времени ПЕРЕД использованием. Лучше медленнее, но точно.**

Не доверять:
- Своей памяти о файле из 10 сообщений назад
- Memory feedback'у как факту (он может устареть, файл переименован, функция удалена)
- Сводке из предыдущей сессии (handoff текст — приблизительный)
- Содержимому файла после auto-compaction
- Аргументам сигнатуры функции, которые «помнишь» — могла измениться
- Структуре Sheets («колонка X = это Y») — могла поехать

Доверять можно:
- Файлам которые читал в этом же turn (sandbox tracks state)
- Содержимому только что выполненной tool call
- Аргументам, переданным в текущем сообщении пользователем

**Точность > скорость. Всегда.** Не экономить шаги/токены на верификации. Между «быстро ответить» и «проверить и ответить точно» — второе. Лишний Read / `stat` / снапшот-чек дешевле, чем порча прода или ложный отчёт. «Быстро» не ценность; ценность — «точно с первого раза».

## Бдительность масштабируется от НЕОБРАТИМОСТИ операции, не от важности задачи

Частый провал: verify-режим включён для «важного» (тщательная сверка чисел — образцово) и выключен для «служебного» (вспомогательный скрипт проверки боевого ресурса). Прод ломается именно в «служебном».

**Класс «необратимое касание состояния» — НЕ бывает служебным**, даже внутри проверочного/вспомогательного скрипта: любая команда, которая ПИШЕТ / СОЗДАЁТ / УДАЛЯЕТ / коннектится к боевому ресурсу (БД, файл на сервере, символлинк, deploy, `rm`/`ln`/`mv`, миграция, мутация внешней таблицы). Для этого класса гейт ПЕРЕД действием не зависит от того, основная это работа или «я только проверю».

Три обязательных чека ПЕРЕД любой такой операцией:
1. **Путь/ресурс — из штатного резолвера/конфига, не из памяти и не хардкод.**
2. **«Просто чтение» боевого ресурса может оказаться записью.** `sqlite3.connect(path)` без `mode=ro` молча создаёт файл-пустышку; открытие файла / парсер / git-команда — убедись, что операция реально read-only (`sqlite3.connect(f"file:{p}?mode=ro", uri=True)`, открытие в режиме `'r'`). Не уверен — считай записью, применяй highest bar.
3. **Действие по гипотезе об инфраструктуре** («там был символлинк», «файл существовал», «конфиг такой») — назвать, ЧЕМ проверю, и проверить ПЕРЕД действием объективным источником (бэкап-снапшот, `stat`, `git log`), не памятью о прошлом выводе.

**Анти-паттерн-маркер:** мысль «это вспомогательный скрипт, проверять не надо» = красный флаг. Тихий fallback (`find`, `try/except`, default-путь) в проверочном скрипте маскирует неверный основной путь — «успешный» вывод не значит, что путь верный; сначала залогируй, КАКАЯ ветка сработала.

**Механический гейт (hook) — написать под свой репо.** Лучшая защита не «помни правило», а PreToolUse-hook, который физически блокирует (exit 2) опасный класс: `connect` к боевой БД без `mode=ro`; `ssh`-мутация прода (`rm`/`ln`/`mv`/перезапись в системных путях). В пэке такого хука нет: пути к боевым ресурсам у каждого свои, поэтому его пишут по месту (пример конструкции — `claude-home/hooks/warn-before-push.sh`). Обход — осознанный: сделать проверки выше, затем явный маркер-комментарий в команде (аналог `--no-verify`). Чтение логов/git, тестовые БД в `/tmp` — не блокировать.

## Триггеры → обязательная проверка ПЕРЕД действием

| Хочу сделать | Обязательно ПЕРЕД |
|---|---|
| Edit формата ячейки/колонки в Sheets | `sheets_read` живой ячейки + проверить Data Validation колонки |
| Edit функции/класса в файле | Read функции (с offset/limit) если прошло >3 сообщений с последнего чтения, или был /compact, или файл >200 строк |
| Использовать сигнатуру функции из памяти | Grep её определение в файле, не вспоминать аргументы |
| Вызвать скрипт / команду | Read implementation скрипта, не помни «он делает X» |
| Утверждать «X пустое / нет данных» | Прочитать ВСЁ X (полный range, не первые 50 строк) |
| Утверждать «файл существует / удалён» | `ls` или `stat` |
| Сравнить или синхронизировать две папки | `ls -ld` обеих ПЕРЕД сравнением: одна может быть символической ссылкой на другую (тогда «копии» и «жёсткие ссылки» мнимые, а удаление в одной сносит оригинал). Все inode подряд совпали — первая гипотеза общий путь, а не жёсткие ссылки |
| Использовать число из памяти / memory feedback | Verify число в исходнике (Sheets / лог / git) |
| Использовать memory feedback как factual claim | Verify актуальность: файл существует, функция не переименована, путь верный |
| Заявить про cron «работает / не работает» | `tail` log на VPS, `systemctl status`, не помни |
| Заявить о структуре Sheets («строка 5 = X») | `sheets_read` конкретного диапазона, не помнить |
| Использовать env-переменную | grep `.env.example` или settings (НЕ читать `.env` — security) |
| Commit | `git status` + `git diff --stat` ПЕРЕД `git add` чтобы увидеть что коммитишь |
| Deploy на VPS | Read deploy скрипт целиком, не помни шаги. После — verify `systemctl status` / smoke |
| Заявить «N коммитов сделано» | `git log --oneline -N` после, не вспоминай |
| Заявить «тесты прошли» | Прогон тестов СЕЙЧАС, не «помню что прошли в прошлой сессии» |
| Утверждение о дате / timestamp | `date` в Bash, не угадывай |
| Заявить «X не работает / 401 / 429» | Прочитать свежий лог ИЛИ запустить повтор, не предполагать |
| Заявить «API отвечает X / ключ не принят» | Тело ответа, не только статус-код: один и тот же код у внешнего API значит разное, и различает их только текст ошибки |
| Использовать импорт / модуль / класс | Grep наличия в codebase, проверить путь |
| Утверждение о канонной методике/формуле проекта | Открыть документ-канон, не интерпретировать на ходу |
| Подключиться к боевой БД | Путь ТОЛЬКО из резолвера/конфига, не хардкод. Чтение — `connect(f"file:{p}?mode=ro", uri=True)` (иначе connect создаёт пустышку) |
| Создать / удалить / слинковать файл на проде (`rm`/`ln`/`mv`) | `stat` цели ПЕРЕД. Гипотеза «там был X» → бэкап-снапшот / `git log`, не память. Подтверждение на удаление (`security.md`) |
| Действие по гипотезе об инфре (символлинк / был файл / конфиг) | Объективная проверка (снапшот / `stat` / `git log`) ПЕРЕД действием, не после |
| «Успешный» вывод проверочного скрипта с fallback | Залогировать, КАКАЯ ветка дала результат (основной путь vs find/except/default) |

## Anti-петля (после 2-й попытки)

Если действие не сработало → ПЕРЕД повторной попыткой:
1. Verify что именно сломалось — прочитать вывод / живую запись / лог, а не угадывать
2. Verify свою гипотезу о причине — открыть код / документацию / Sheets, не помнить

**После 2-й идентичной попытки с одним симптомом → СТОП.** Спроси у пользователя точный ожидаемый результат, не пытайся 3-й раз. Цикл «фикс → не работает → фикс → не работает» = маркер что причина не та, которую ты предполагаешь.

См. также `rules/loop-detection.md`.

## Что НЕ нужно перечитывать (исключения чтобы не зашиться)

- Файл прочитанный в этом же turn (sandbox tracks state — Edit без повторного Read OK)
- Содержимое tool call'а, выполненного только что
- Аргументы, переданные пользователем в текущем сообщении
- Очевидные технические факты (Python синтаксис, оператор сравнения) — но если есть СОМНЕНИЕ, проверь
- Инструкции текущего агента (`AGENTS.md` для Codex, `CLAUDE.md` для Claude Code) и `rules/`, уже загруженные в текущую сессию

## Конкретные классы багов которые это правило закрывает

- **Хардкод vs живой источник** — код думал, что список/валидатор захардкожен актуально, а реальная конфигурация во внешней системе изменилась
- **Правка формата без чтения живой ячейки/значения** — несколько итераций вслепую вместо одного взгляда на реальные данные
- **«Колонка/поле пустое»** — вывод после чтения только первых N строк большого файла
- **False positives аудита** — claim про код без открытия реального файла
- **«Функция работает не так»** — без прогона на реальном API/данных
- **Действие на основе непроверенного измерительного инструмента** (сначала прогони валидатор на кейсе с известным ответом)
- **Память/заметка устарела** — функция уже переименована, путь изменился
- **Хардкод пути к боевой БД + connect-пустышка** — `connect` к несуществующему хардкод-пути создал пустую БД на проде; fallback замаскировал; гипотеза об инфре → правка по памяти
