# Защита бизнес-логики от случайного переписывания

## Зачем

Заметная доля «фиксов» от ИИ-аудитов на самом деле **ломает работающие метрики**. Типичный сценарий:

1. ИИ читает код функции (агрегация / классификация / формула / маппинг).
2. Видит, что код делает X, а comment / note / документация описывает Y.
3. Решает «code-vs-doc drift, чиню».
4. Переписывает код на Y.
5. В проде ломаются числа.
6. Никто сразу не замечает (метрика выглядит «правдоподобно», просто другая).
7. Через дни/недели — пользователь замечает аномалию.

**Типичный инцидент:** note у поля говорил одно, код считал другое. ИИ счёл это багом и переписал код «под note», исказив метрику, прогнал backfill, потом откатил по сигналу пользователя. На деле код был правильный, а note — неудачно сформулирован. Источник истины оказался в коде, а не в подписи к нему.

## Правило

**При работе с бизнес-логикой (метрики, агрегации, формулы, классификации) запрещено переписывать функцию без всех трёх условий:**

1. **Явный запрос пользователя** с конкретным симптомом («цифра X в позиции Y неверная, должна быть Z»).
2. **Воспроизводимое доказательство бага**: фиксированный вход + ожидаемое значение + текущее значение + источник истины (выгрузка / live API call / документ).
3. **Подтверждение**, что новая логика даёт ожидаемое значение на этом тест-кейсе.

**Note / comment / документация — НЕ источник истины.** Они могут быть устаревшими, неудачно сформулированными, изначально неверными. Источник истины — **рабочий код в проде** + **поведение, которое пользователь подтверждает как правильное**.

При обнаружении расхождения «note говорит X, код делает Y»:
- НЕ менять код по своей инициативе.
- Спросить пользователя: «note говорит X, код делает Y, в проде цифра соответствует Y. Что считать правильным?»
- Если правильно Y — обновить note (не код).
- Если правильно X — попросить тест-кейс, прежде чем трогать код.

## Маркер SEALED-LOGIC

Критические бизнес-логические блоки помечаются в коде комментарием-обёрткой:

```python
# SEALED-LOGIC START — <название метрики>
# Семантика: <короткое описание что считает>
# Источник истины: <как проверить — выгрузка / live API / отчёт>
# История: <дата ввода + ссылка на инцидент если был>
... код ...
# SEALED-LOGIC END
```

Тот же маркер на другом языке (`// SEALED-LOGIC START` и т.д.).

**Enforcement.** Pre-commit hook, который при правке внутри `SEALED-LOGIC`-блока требует в commit message флаг **`[bizlogic-change-approved]`**; без флага — отбрасывает коммит. Это превращает «помни правило» в механический гейт.

## Реестр SEALED-блоков

Заведи в проекте таблицу всех помеченных функций (файл, функция, что защищает) и пополняй её по мере выявления критичных мест. Список — это карта «куда нельзя лезть без тест-кейса».

## Как добавить SEALED в новое место

1. Обернуть функцию маркерами `START` / `END`.
2. Заполнить семантику + источник истины + ссылку на инцидент (если есть).
3. Добавить строку в реестр.
4. Закоммитить с `[bizlogic-change-approved]` (первое введение — это тоже изменение SEALED-блока).

## Bypass

Если правка точно осознанная и подтверждена пользователем:
- Добавь `[bizlogic-change-approved]` в commit message.
- Или (крайний случай) `git commit --no-verify`.
