# Планы крупных работ

Перед началом крупной работы — создать план как отдельный файл в `<project>/plans/`. План живёт в git, не теряется при смене сессии, читается первым любой новой сессией или внешним ИИ (Codex, Gemini).

## Когда план НУЖЕН

Хотя бы одно из:
- Работа растянется на 2+ сессий (нельзя закрыть в одну).
- 3+ независимых шагов с зависимостями (миграция БД, новая фича с тестами+деплоем+уведомлением).
- Затрагивает deploy на прод / схему БД / production-конфиги или формулы.
- Кросс-проектная (затрагивает 2+ модуля/папки проекта).

## Когда план НЕ нужен

- Bugfix (даже сложный — план = git-комит + описание в commit message).
- Косметика UI, переименования, мелкие правки документации.
- Одноразовые скрипты в `_done/`.
- Codex round правки (есть промт в `/tmp/` — он и есть план).

## Где живёт

`<project>/plans/YYYY-MM-DD-<slug>.md`. Один проект — одна папка `plans/`. Создаётся при появлении первого плана, до этого папки нет.

Закрытые планы (status: done / отменён / исполненный отчёт) — в `<project>/plans/archive/`: `plans/` по glob показывает только живое. Перемещение — `git mv` + правка ссылок в живых доках (исторические changelog/decisions/handoffs не трогаем).

Примеры:
- `infra/plans/2026-05-19-postgres-migration.md`
- `webapp/plans/2026-06-01-new-panel.md`
- `<module>/plans/YYYY-MM-DD-feature-onboarding.md`

Файл append-only — НЕ удаляется после завершения. Закрытость отражается полем `status: done` в frontmatter + строкой в корневом `## Status` (см. ниже).

## Шаблон

```markdown
---
created: YYYY-MM-DD
status: active        # active | done | abandoned
owner: <имя>          # кто отвечает
related:
  - <doc>.md §N        # навигация к контексту
  - rules/<rule>.md
---

# Краткое название работы

## Цель
Одно предложение — что в итоге должно быть.

## Зачем (бизнес-причина)
Чем эта работа решает реальную проблему. Если непонятно — фича не нужна.

## Не делаем (out of scope)
- ...

## Инварианты — не нарушить
- ...
- ...

## Шаги

- [ ] **1. Что-то конкретное**
  - Команды:
    ```bash
    python3 ...
    ```
  - Проверка: ожидаем `OK xxx`.
  - Коммит:
    ```
    feat(scope): описание
    ```

- [ ] **2. Следующее**
  - ...

## Открытые вопросы
- ...

## Журнал
- 2026-05-19: создан
- 2026-05-21: шаги 1-3 выполнены, ssesion-1 закрыта
```

## Правила работы с планом

- Начало любой сессии по крупной работе — открыть план первым, продолжать с первого `- [ ]`.
- Закрытый шаг отмечается `- [x]` + коротко что сделано (одна строка после строки).
- Если упёрлись в блокер — добавить в `## Открытые вопросы`, остановить работу, обсудить с пользователем.
- При завершении работы — `status: done` в frontmatter + ссылка в корневом `## Status` обновляется.
- При сворачивании сессии (handoff) — план уже актуален, отдельный «промт для следующей сессии» не нужен.

## Корневой `## Status`

В корневом `CLAUDE.md` есть короткая секция `## Status — крупные работы`. Это табло «что в системе»: активные планы со ссылками, недавно закрытые (последние 5-7), и запланированные. Не дублирует `decisions.md` — там длинная история, тут только активная линия.

При создании нового плана — сразу добавить строку в `## Status` (`🔄 active`). При закрытии — заменить на `✅ done` + дата. Через 2-3 месяца закрытые строки можно сворачивать (оставлять последние 5), история всё равно в git + `plans/` папке.

Codex это табло не читает и не меняет: источник статуса для него — frontmatter и чекбоксы файлов `<project>/plans/*.md`; при создании и закрытии плана Codex обновляет сам план и нейтральные `context.md` / `decisions.md`.
