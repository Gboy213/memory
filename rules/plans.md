# Планы крупных работ

Перед началом крупной работы — создать план как отдельный файл в `<project>/plans/`. План живёт в git, не теряется при смене сессии, читается первым любой новой сессией или внешним ИИ.

## Когда план НУЖЕН

Хотя бы одно из:
- Работа растянется на 2+ сессий (нельзя закрыть в одну).
- 3+ независимых шагов с зависимостями (миграция БД, новая фича с тестами+деплоем+уведомлением).
- Затрагивает deploy на сервер / схему БД / структуру данных / production-формулы.
- Кросс-проектная (затрагивает 2+ модуля репозитория).

## Когда план НЕ нужен

- Bugfix (даже сложный — план = git-комит + описание в commit message).
- Косметика UI, переименования, мелкие правки документации.
- Одноразовые скрипты.
- Аудит-правки по готовому промту (промт сам и есть план).

## Где живёт

`<project>/plans/YYYY-MM-DD-<slug>.md`. Один модуль — одна папка `plans/`. Создаётся при появлении первого плана, до этого папки нет.

Примеры:
- `<backend>/plans/2026-XX-XX-db-migration.md`
- `<frontend>/plans/2026-XX-XX-new-feature.md`
- `<infra>/plans/2026-XX-XX-deploy-overhaul.md`

Файл append-only — НЕ удаляется после завершения. Закрытость отражается полем `status: done` в frontmatter + строкой в корневом `## Status` (см. ниже).

## Шаблон

```markdown
---
created: 2026-XX-XX
status: active        # active | done | abandoned
owner: <имя>
related:
  - <path>/context.md §...   # навигация к контексту
  - rules/<...>.md
---

# Краткое название работы

## Цель
Одно предложение — что в итоге должно быть.

## Зачем (бизнес-причина)
Чем эта работа решает реальную проблему. Если непонятно — фича не нужна.

## Не делаем (out of scope)
- ...

## Инварианты — не нарушить
- ...
- ...

## Шаги

- [ ] **1. Что-то конкретное**
  - Команды:
    ```bash
    <команда>
    ```
  - Проверка: ожидаем `OK xxx`.
  - Коммит:
    ```
    feat(scope): описание
    ```

- [ ] **2. Следующее**
  - ...

## Открытые вопросы
- ...

## Журнал
- 2026-XX-XX: создан
- 2026-XX-XX: шаги 1-3 выполнены, session-1 закрыта
```

## Правила работы с планом

- Начало любой сессии по крупной работе — открыть план первым, продолжать с первого `- [ ]`.
- Закрытый шаг отмечается `- [x]` + коротко что сделано (одна строка после строки).
- Если упёрлись в блокер — добавить в `## Открытые вопросы`, остановить работу, обсудить с пользователем.
- При завершении работы — `status: done` в frontmatter + ссылка в корневом `## Status` обновляется.
- При сворачивании сессии (handoff) — план уже актуален, отдельный «промт для следующей сессии» не нужен.

## Корневой `## Status`

В корневом `CLAUDE.md` рекомендуется короткая секция `## Status — крупные работы`. Это табло «что в системе»: активные планы со ссылками, недавно закрытые (последние 5-7), и запланированные. Не дублирует `decisions.md` — там длинная история, тут только активная линия.

При создании нового плана — сразу добавить строку в `## Status` (`🔄 active`). При закрытии — заменить на `✅ done` + дата. Через 2-3 месяца закрытые строки можно сворачивать (оставлять последние 5), история всё равно в git + `plans/` папке.

## Зачем это вообще

В чате план умирает с сессией. После `/compact` или новой сессии теряются: какие шаги уже сделаны, какие команды протестированы, какие коммиты ожидаются. План в git решает это — любая новая сессия восстанавливает контекст за 30 секунд.

Идея заимствована из практики автора tntfy ([github.com/zjor/tntfy](https://github.com/zjor/tntfy)): `docs/project/plans/<date>-<feature>.md` с пошаговым TDD-чек-листом и готовыми commit-сообщениями. Адаптировано под domain-driven монорепо: план кладётся в папку модуля, а не централизованно в `docs/`.
