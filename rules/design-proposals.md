# Дизайн-предложения (UI / UX)

## Триггер

Когда пользователь говорит **«предложи дизайн X»**, **«редизайн X»** или явно описывает задачу на переработку интерфейса (модалка, форма, страница, блок, компонент) — **не лезть сразу в код**. Сначала пройти 5 пунктов согласования, получить «ок» или правки, только потом править файлы.

Также триггерится при фразах: «нарисуй», «перерисуй», «задизайнь», «переделай модалку/форму/страницу», «сделай UI для…».

## Формат ответа (5 пунктов)

1. **В чём проблема текущего окна/блока** — 3-6 буллетов. Конкретно: где шумно, где теряется фокус, где одинаковый вес у разных по важности вещей, что занимает больше места чем заслуживает.
2. **Новая структура блоков** — ASCII-схема или нумерованный список уровней. Что идёт сверху, что под чем, как сгруппировано.
3. **Таблица контролов** — по каждому полю: «было → стало → почему». Не пропускать ни одного поля из текущего интерфейса.
4. **2-4 приёма визуальной лёгкости** — нумерованный список. Каждый приём даёт измеримое улучшение (меньше рядов, меньше шума, единая сетка). Без абстракций типа «добавим воздуха».
5. **Текстовый wireframe** — ASCII-макет окна/блока с реальными примерами значений, не «Lorem ipsum». Должен влезать в одно сообщение.

После пункта 5 — короткий вопрос: «Делать? Если да — перечень файлов которые буду трогать.»

## Жёсткие запреты в дизайн-предложении

- Не предлагать убирать поля (если это не разрешено явно).
- Не делать wizard / пошаговую форму, если не просили.
- Не предлагать «красивый концепт» — только прагматичный CRM-style, который можно внедрить за один коммит.
- Не писать CSS/HTML в ответе-предложении. Только структура, контролы, wireframe.
- Не добавлять декоративные элементы (градиенты, тени, иконки ради иконок) — по умолчанию всё должно быть плоским и функциональным.

## После согласования

- Менять только то, что описано в предложении. Не прихватывать «ещё пару мелочей» — это отдельная задача.
- Проверять что бизнес-логика и состав полей не изменились, если пользователь явно не попросил.
- Прогнать тесты проекта (если есть) перед деплоем.
- В коммит-сообщение попадают: блок из пункта 2 (новая структура) + список изменённых файлов.
