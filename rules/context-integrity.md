# Целостность контекста и верификация

## Проблема

Read читает с лимитом (2000 строк / ~25K токенов); при auto-compaction ранние сообщения сжимаются — содержимое файлов и промежуточные решения теряются. После 15+ сообщений можно галлюцинировать имена переменных и ломать только что понятое.

## Чтение файлов

- **Файл >500 строк** — читать чанками (offset/limit по 500); не доверять одному Read на большой файл
- **Перед правкой** — перечитать файл, если >3 сообщений с последнего чтения или файл >200 строк. Не править по памяти из ранних сообщений
- **После правки** — перечитывать целиком только если правка сложная или файл большой; синтаксис проверяет хук (ниже)

## Верификация изменений

### Код
- **Синтаксис .py/.json/.sh/.js проверяет хук после каждого Edit/Write** (Claude: `~/.claude/hooks/post-edit-syntax-check.sh`; Codex: свой на apply_patch) — вручную ast/node --check не гонять. Другие форматы (YAML и пр.) — парсером вручную
- **Есть тесты** — прогнать после правки

### Конфиги и данные
- **JSON/YAML** — проверить парсером
- **Google Sheets формулы** — после записи прочитать ячейку обратно
- **HTML** — открыть в браузере или проверить структуру

### Деплой
- **После git push** — проверить что прошёл (exit code + output); **после systemctl restart** — `systemctl status`; **после rsync** — файлы долетели
- **Деплой на сервер** — ВСЕГДА `git commit` → `git push` → deploy, не наоборот: если сервер сам подтягивает git по cron, ручной деплой будет перезаписан. После программной правки HTML — `grep -c 'ключевые_id' файл`
- **«Готово» — только с доказательством проверки** (вывод health, цифра/строка из прода, зелёный тест) — деплой сам по себе не доказательство
- **Правка cron-канала** (сбор данных, адаптер, лог): доказательство = первая строка в логе канала на сервере после первого прогона с новым кодом. Коммит и pull на сервер доказательством не являются: код доезжает за минуты, а поведение видно только со следующего запуска по расписанию. До этого писать «ждём прогон в HH:MM», не «починено»

### UI / CSS после переноса макета в прод
- **«HTML и CSS 1-в-1 с макетом ≠ рендер 1-в-1».** Разный каскад, родители, reset, версия движка — дают разный computed size на одинаковом CSS.
- **После переноса компонента** — сразу попросить пользователя прислать DevTools-скрины computed size контрольных элементов (строка таблицы, высота футера, заголовок) и сравнить с макетом. Не отчитываться «готово» по факту деплоя.
- **Известные ловушки:**
  - `box-sizing: border-box` **не работает надёжно на `<th>` / `<td>`** (W3C-спека). Не комбинировать `padding: V H` + `height: Y` на table cells. Паттерн: `padding: 0 H; height: Y` + `vertical-align: middle; line-height: 1`.
  - `zoom: X` применяется разными алгоритмами к flex-items и inline-width элементам — накапливает subpixel-разъезд на длинных сетках.
  - Глобальный `* { box-sizing: border-box }` может быть перебит user-agent stylesheet'ом для table cells.
- **Контроль высоты:** `total_height = height + vertical_padding + vertical_border`, если box-sizing не гарантирован. Нужно ровно `Y px` — вертикальный padding `0`, остальное через `line-height` / `vertical-align`.

## Документы: правило секционного split

- **Документ >500 строк** — кандидат на секционный split: индекс с ToC + `docs/<slug>.md` рядом.
- Содержимое секций переносить дословно, верифицировать поблочным diff против оригинала.
- Индекс не удалять: ссылки вида «file.md § X» из кода и других доков резолвятся через ToC индекса — обратная совместимость без правки сотен ссылок.
- Новые большие справочники сразу писать секционно, а не монолитом.

## Длинные сессии (10+ правок)

- На 10-м и 20-м сообщении — перечитать рабочие файлы (ранний контекст мог сжаться)
- Путаю имена/номера строк — стоп, перечитать; чувствую потерю контекста — предложить /compact

## Принцип

Не доверяй exit code 0, «успешно записано» и своей памяти о файле из 10 сообщений назад. Открой и проверь.
