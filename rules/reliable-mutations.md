# Надёжные изменяющие операции

Чеклист перед написанием кода, который меняет состояние: деньги, договоры,
облачные папки, внешние таблицы, БД, бэкапы, фоновые воркеры. Итог четырёх раундов
внешнего аудита: почти все найденные баги — один класс, «упал на середине и соврал
об успехе». Для read-only кода не нужен.

## Инвариант

**Cleanup не уничтожает сведения, нужные для retry/recovery, пока сам
cleanup не завершился успешно.** (Пример: pending-запись удаляется только
после подтверждённого Drive-delete или 404.)

## Обязательные вопросы (ответить до кода)

1. Где точка commit — после какого шага операция «случилась»?
2. Что будет, если процесс умрёт до / после commit? После рестарта?
3. Можно ли безопасно повторить? Какой ключ идемпотентности?
4. Частичный отказ (1 из N наборов упал) — виден ли он в rc/алерте,
   или тонет в общем «успехе»? Тихий rc=0 при потере данных запрещён.
5. Кто второй может бежать параллельно? Какой лок/транзакция защищает шов?
6. Как оператор вручную докатит/откатит зависшую операцию?

## Классы реализации (выбрать по ситуации)

1. **Одна БД** → одна транзакция (BEGIN IMMEDIATE), и всё.
2. **Файл** → уникальный temp (`.build.<pid>`) → проверка → atomic replace →
   cleanup только своего temp. Прошлый корректный файл жив при сбое.
3. **Несколько внешних систем** (Drive+master, API+Sheets) → порядок шагов,
   при котором сбой любого шага оставляет операцию повторяемой; журнал
   pending с TTL.
4. **Очередь/воркер** → атомарный переход состояния под одним локом,
   повтор идемпотентен, вечный цикл невозможен.
5. **Бэкап** → staging → содержательная проверка (integrity, manifest,
   непустота) → atomic publish (latest переключается последним). Живые
   WAL-БД — только SQLite `.backup`, не file-copy.

Общий helper выделять только при 3+ реально одинаковых реализациях —
не строить framework заранее.
