# Долгая память между сессиями

Claude не помнит вчерашний разговор. Каждая новая сессия начинается с нуля. Чтобы он не задавал одни и те же вопросы и не повторял одни и те же ошибки, мы складываем «память» в обычные markdown-файлы внутри git-репозитория (или в локальный кэш `~/.claude/projects/...`).

## Структура

```
memory/
├── README.md          ← этот файл
├── MEMORY.md          ← короткий index со ссылками на файлы ниже
├── user_*.md          ← факты о пользователе
├── feedback_*.md      ← мягкие предпочтения и validated approaches
├── project_*.md       ← контекст проекта
└── reference_*.md     ← где искать актуальную информацию вне репо
```

`MEMORY.md` — оглавление, **всегда** загружается в контекст. Держи его коротким (под 200 строк), однострочные ссылки на конкретные файлы.

Отдельные `<type>_<name>.md` — содержание. Загружаются лениво, когда становятся релевантны.

## Типы памяти

### user
Информация о роли пользователя, его опыте, контексте работы.

**Когда писать:** узнал что-то о пользователе — роль, специализация, что любит/не любит.
**Как использовать:** адаптировать стиль ответа под профиль (senior dev ≠ no-coder).

### feedback
Мягкие предпочтения и подтверждённые подходы.

**Когда писать:**
- Пользователь дал прямую коррекцию («не делай так»).
- Пользователь подтвердил неочевидный подход без правок («да, именно так»).

Записывать не только корректировки, но и validated approaches — иначе агент будет аккуратен в избегании прошлых ошибок, но забудет одобренные паттерны.

**Структура:** правило в одну фразу + **Why:** (почему пользователь так решил, какой инцидент за этим стоит) + **How to apply:** (когда применять, edge cases).

### project
Состояние и контекст проекта: кто что делает, к какому сроку, по какой причине.

**Когда писать:** услышал бизнес-обстоятельство (релиз, заморозка, миграция, поставщик меняет API).
**Как использовать:** учитывать при предложениях («не делай этого в неделю заморозки»).

**Структура:** факт + **Why:** + **How to apply:**.

Переводи относительные даты в абсолютные («во вторник» → «2026-05-20»), иначе через неделю запись теряет смысл.

### reference
Указатели на актуальную информацию вне репо: дашборды, базы, Slack-каналы, документация внешних API.

**Когда писать:** услышал «там лежит / там обсуждают».
**Как использовать:** при упоминании этой темы — направить к нужному источнику.

## Формат файла памяти

Каждый файл — один факт с frontmatter (по нему Claude Code решает, релевантна ли память):

```markdown
---
name: <короткий-slug>
description: <одна строка — о чём, для поиска>
metadata:
  type: user | feedback | project | reference
---

<сам факт; для feedback/project — далее строки **Why:** и **How to apply:**.
Связанные памяти — ссылками [[slug-другой-памяти]].>
```

После записи файла — одна строка-указатель в `MEMORY.md` (`- [Заголовок](file.md) — суть`). В `MEMORY.md` только указатели, без содержимого.

## Что НЕ писать в memory

- Правила поведения Claude (всегда делай X / никогда не делай Y) → это в `rules/*.md` под git
- Архитектурные решения → `<project>/decisions.md`
- Код-структуру → она в самом коде
- API-ключи, секреты → НИКОГДА
- Содержимое читанных файлов (компрессия context'а не сохраняет факты, а файл всегда можно прочитать снова)

## Когда обращаться к memory

- Когда тема явно связана с предыдущим опытом пользователя
- Когда упомянут проект, человек, инцидент — открыть соответствующий файл
- Когда Claude собирается сделать что-то, что раньше пользователь критиковал — проверить feedback_*

## Stale entries

Память может устаревать. Раз в 2-3 месяца — review:
- Что устарело (упоминания версий/сервисов которых уже нет)?
- Что повторяется в разных файлах?
- Что не применялось ни разу?

Stale entries удалять / переписывать. Идея: «memory всегда меньше чем хочется».
