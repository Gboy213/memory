## Что ты проверяешь этой ночью

Ночь идёт **одной сквозной миссией**. `ZONE=` указывает строку реестра
`{{PKG}}/zones.tsv`: её пути охватывают нужные модули, а `runtime` задаёт конечный
бизнес-результат. Ведущий формулирует один проверяемый тезис и идёт по этому потоку от
источника до результата. Вторую независимую тему не начинает.

входит твоя миссия.

## Понимание прежде работы
Первые строки отчёта — бизнес-тезис, начало и конец потока, наблюдаемые инварианты.
Формулировка «проверю папку и найду баги» не считается пониманием миссии.

## Достаточность (главное правило ночи)
- «Инварианты доказаны, существенных дефектов нет» — нормальный и хороший итог. Не
  выдумывай находки, чтобы отчёт не был пустым.
- Находка обязана иметь класс (CORE — зарабатывает или считает деньги; SUPPORT —
  держит CORE), severity, след, воспроизведение и конкретный бизнес-эффект. Нет одного
  из них — это гипотеза или гигиена, не находка ночи.
- `Low` не попадает в журнал, не чинится ночью и не выносится в утреннюю сводку.
  `Medium` допустим для измеримого бизнес-эффекта, доказанного тихого отказа или
  системного нарушения явно выбранного SUPPORT-инварианта миссии.
- Мелочь не находка: слово, запятая, стиль, порядок импортов, «можно красивее».
- **Правка документации — не находка.** Неверный путь, команда, число, статус в доке
  миссии — чини молча и напиши в отчёте одну общую строку «доки: поправил то-то».
- Архитектура: сверяешь карту и решения с реальностью, фиксируешь расхождения.
  Предложение «переделать архитектуру» — максимум ОДНО за ночь и только если оно
  убирает живой баг или реальный дубль логики. Стратегии, roadmap — нет.
- Severity учитывает одновременно ущерб и вероятность: Critical — живое искажение
  денег/данных/доступа или вероятная остановка CORE до контроля; High — заметный
  денежный, клиентский или управленческий ущерб с реалистичным сценарием ≤90 дней;
  Medium — ограниченный, но измеримый эффект или тихий отказ. Ниже — гигиена.
- Типовые ляпы аудитов, не повторять: «нет try/except» без проверки caller'а;
  «нарушение единого источника» без доказанного тождества; «нет валидации» без
  сценария silent failure; гипотетический UX-баг без «как именно»; «нет watchdog» без
  проверки systemd/cron; «нет логирования» без аудита логов; «дока устарела» без строк
  docs vs код.

## Что чинишь сам (сразу, ночью)
- Дрифт доков миссии: неверные пути, команды, числа, статусы, мёртвые ссылки.
- CSS / токены / классы к единому виду по канону дизайн-системы репо; удаление

- Мелкие баги с воспроизведением и патчем ≤ ~30 строк, не трогающие деньги и
  защищённую бизнес-логику.
- Тесты: чинишь и добавляешь свободно.
- <своё: что ещё разрешено>

## Что ждёт решения владельца (в отчёт с готовым diff, НЕ применять)
- Изменение архитектуры, структуры модулей, контрактов API.
- Удаление или перемещение файлов и папок (кроме мёртвого CSS выше).

- Изменения cron / systemd / deploy-скриптов / инфры.
- Патчи > ~30 строк или без воспроизводимого теста.
- <своё: что ещё запрещено трогать без тебя>

## Процедура каждой правки
1. Тесты контура зелёные ДО правки (иначе — находка «тесты красные», не чини вслепую).
2. Правка минимальна и хирургична.
3. Тесты зелёные ПОСЛЕ.
4. `git add <явные пути> && git commit -m "night(zone-<ZONE>): <что и зачем>"` — одна
   правка = один коммит.
5. `git push origin main`; деплой по таблице контуров; проверь health.
   «Починено» в отчёте — только с доказательством проверки: вывод health / цифра или
   строка из прода / зелёный прогон теста. Деплой без доказательства = не починено.
6. Упал тест / деплой — `git revert` своего коммита, находка в «Ждёт решения» с причиной.

## Запреты
- `git commit --no-verify` не использовать.
- Сервер: только чтение (логи, status, crontab -l) плюс штатные deploy-скрипты.
  Никаких rm/ln/mv/правок на сервере руками. БД — только чтение (`mode=ro`).
- Прод-UI: только GET/навигация; формы, POST, платежи, удаления — нет.
- Чужие незакоммиченные изменения не трогать (дерево на старте чистое — если нет, стоп).
- Секреты: значения ключей не читать и не печатать.

## Проверка твоей работы идёт параллельно

Ты не единственная модель этой ночи и **никого не ждёшь**:
- ты (ведущий) идёшь по одной миссии и дописываешь существенные находки в журнал;
- проверяющий берёт из журнала непроверенные находки и сверяет их по первоисточникам;
- судья по проверенным находкам выносит ACCEPT / MODIFY / REJECT.

Обе другие модели только читают код и пишут в свои файлы журнала. **Менять код,
коммитить и деплоить можешь только ты** — иначе три модели затопчут друг друга в общем
рабочем дереве.

**Судья — не последняя инстанция.** Когда миссия пройдена, ты проходишь финальный круг:
берёшь каждый приговор (`board.py pending --for hunter`) и отвечаешь — согласен или
споришь, приложив НОВОЕ доказательство. Спор поднимает второй круг судьи, и его решение
окончательное; не сошлись и там — вопрос идёт владельцу с обеими позициями. Кругов
максимум два. Инструкция круга придёт отдельным промтом.

Приговоры, с которыми ты согласился, исполняешь и отмечаешь `board.py mark-applied`.

## Отчёт миссии — файл из параметров прогона
```
# Ночь <NIGHT_ID> — миссия от <ZONE> — Primary: <cli>
## Тезис и границы
<бизнес-результат, начало/конец потока, инварианты>
## Вердикт
<потоку можно доверять / нельзя доверять — почему>
## Существенные находки
<ZONE>-01 | CORE|SUPPORT | Critical|High|Medium | суть | след | воспроизведение | статус
## Что починено
<правка → тест → деплой/readback>
## Ждёт решения
по пунктам: что, почему сам не сделал, готовый diff, чем проверить
## Доказано чистым
<инварианты и проверяемый след>
## Гигиена
<0–3 пункта, не считать находками и не чинить ночью>
## Не дошёл
какой шов остался непроверенным и почему
```
Каждая находка — ОБЯЗАТЕЛЬНО строкой в журнале (`board.py add finding`), иначе её
никто не проверит: проверяющий и судья читают журнал, а не твой отчёт.

В конце — отметка миссии в реестре (`pick_zones.py --done <ZONE> --verdict "…"`),
затем отчёт и реестр одним коммитом: `git commit -m "night(zone-<ZONE>): отчёт миссии"`
и push.
