# Close Session

При срабатывании — стоп. Бросить текущую работу. Цель не передать контекст другой сессии прямо сейчас, а зафиксировать состояние так, чтобы будущий ты (через день, неделю, месяц) мог вернуться без потерь.

Главная боль которую закрывает скилл: пользователь закрывает терминал → контекст теряется → через неделю не помнит на чём остановился, какие подходы отвергал, какие вопросы оставались открытыми.

## Чем close отличается от handoff

| | handoff | close |
|---|---|---|
| Когда | «сейчас открываю новую сессию» | «закрываю терминал, может вернусь когда-то» |
| Буфер | да, готовый промт через pbcopy | нет, копировать сейчас некуда |
| LEFT | ровно 1 пункт (с чего начать сразу) | OPEN: может быть несколько (полный список) |
| Тупики | не обязательно | обязательно — DEAD ENDS |
| Развилки | не обязательно | обязательно — QUESTIONS |
| Recipient | следующая сессия Claude | будущий ты + следующая сессия Claude |
| Финал | «можно делать /compact или новую сессию» | «контекст зафиксирован, можно закрывать терминал» |

При неоднозначности (пользователь сказал «хватит на сегодня» без уточнений) — спросить одним вопросом:
> Идёшь сейчас в новую сессию или просто закрываешься?

## Когда триггерить

**Явные триггеры:**
- «закрываю сессию», «сессию закрываю»
- «закрываю терминал», «выхожу», «отключаюсь»
- «спать пошёл», «всё на сегодня, закрываюсь»
- «зафиксируй контекст», «сохрани всё перед закрытием»
- «хватит, просто закрой»

**НЕ триггерить если в фразе есть:**
- «новая сессия», «сделай промт», «промт для продолжения» → `/handoff`
- «переходим дальше», «продолжим в новой» → `/handoff`
- «context is running low» → `/handoff` (контекст вот-вот сожмётся, лучше передать)

## Принцип построения close-snapshot

Как в handoff: **указывай на источники истины, а не пересказывай их.** Реальное состояние = живые файлы + git + БД. Снапшот указывает где смотреть, не пытается воспроизвести содержимое.

Разница с handoff: в close важнее **полнота**, чем краткость. Через неделю детали забудутся, и каждая пометка «почему не пошли по варианту X» сэкономит время при возврате. Лучше 30 точных строк, чем 15 размытых.

## Step 1: Понять что изменилось в сессии

```bash
git status -u
git diff --stat HEAD
git log --oneline -5
```

Если working tree clean и нет новых коммитов — отметить явно: «сессия была exploratory» или «всё закоммичено».

## Step 2: Обновить документацию проекта

ТОЛЬКО то что реально изменилось. Не трогать актуальные файлы.

Файлы (если есть в проекте):
- `current-focus.md` — что сделано, что осталось, блокеры
- `decisions.md` — новые решения, не записанные ранее
- `context.md` — структурные изменения (новые сущности, переименования)
- adapter текущего агента (`CLAUDE.md` для Claude Code, `AGENTS.md` для Codex/Kimi, `QWEN.md` для Qwen) — если изменились команды, пути, ссылки. Чужие adapter-файлы не читать и не менять

Все рабочие артефакты должны быть сохранены в проекте, не остаться только в чате.

Guardrails (любой CLI): следовать инструкциям своего adapter-файла; не читать файлы, запрещённые инструкциями репо; сохранить все правки пользователя; не коммитить, не пушить, не деплоить, не удалять данные, не продолжать продуктовую работу; не включать секреты, персональные данные, сырые выгрузки БД и большие диффы; не заявлять, что сохранён весь разговор.

## Step 3: Собрать close-snapshot в строгом формате

```
project: [название]
domain: [узкий домен, не широкая тема]
session: N
date_closed: YYYY-MM-DD HH:MM
last_commit: [SHA + первая строка сообщения]
git_status: clean | dirty (список файлов если dirty)
files_in_focus:
  - [path/to/file] ([состояние])
  - [path/to/file]
prev_handoff: [.handoffs/файл если есть, null если первая сессия]

## DONE
- [конкретное действие с указателем (SHA / file:line)]
- [конкретное действие с путём]

## OPEN
- [открытая задача 1 с критерием готовности]
- [открытая задача 2]
- [открытая задача 3]

## DEAD ENDS
- [подход X не сработал, причина: Y. Не повторять при возврате]
- [вариант Z отвергнут пользователем словами «...». Не предлагать снова]

## QUESTIONS
- [неотвеченный вопрос 1, кто/что блокирует ответ]
- [открытая развилка 2, варианты ABC]

## RETURN POINT
Когда вернёшься (через день/неделю/месяц):
1. Прочитай: [список файлов через запятую]
2. Проверь актуальность DONE — что-то могло измениться (коммиты других, изменения в Sheets, реакция партнёров и т.п.)
3. Реши с чего продолжать из OPEN — по приоритету или по контексту дня
```

**Правила:**
- DONE = факты с указателями (SHA, file:line, путь файла), не пересказ
- OPEN = действия с критерием готовности («отправить записку и получить реакцию» — не «общаться с партнёрами»)
- DEAD ENDS обязательно если в сессии были отвергнутые подходы. Это страховка от повторения
- QUESTIONS обязательно если остались открытые развилки. Декай у вопросов быстрее всего
- RETURN POINT = инструкция для возврата, не предписание сессии Claude. Может содержать «спроси у пользователя X» если данные могли устареть
- Без em-dash «—», без mini-summary в конце, без «надеюсь продолжишь успешно» — `rules/writing.md § HARD BANS`

## Step 4: Сохранить файл

`<project>/.handoffs/YYYY-MM-DD-HHMM-close-<slug>.md`

Префикс `close-` в имени файла отличает от handoff. Папка та же — `.handoffs/`, чтобы `rules/session-start.md` находил оба формата при следующем открытии сессии.

**НЕ делать pbcopy.** Пользователь закрывается, копировать некуда. Буфер останется с предыдущим содержимым — не трогать, чтобы не создавать ложного впечатления что есть какой-то промт для вставки.

## Step 5: Финальный отчёт пользователю

Одно короткое сообщение:
> Контекст зафиксирован в `.handoffs/2026-05-26-2300-close-<slug>.md`. Открытых задач: N, тупиков: M, открытых вопросов: K. Можно закрывать терминал.

Без «спасибо за работу», без «до встречи», без «удачи». Без зеркалирования эмоций пользователя.

## Что делает сессия Claude при возврате через close

Описано в `rules/session-start.md`. Кратко:
1. Стартовый скрипт проверяет свежие файлы в `<project>/.handoffs/` за последние 24ч
2. Если найден `close-*.md` — это сигнал «пользователь возвращается после закрытия». Прочитать close-snapshot целиком, особенно DEAD ENDS и QUESTIONS
3. Если close старше 24ч — упомянуть «есть close от DATE по теме X, читать?»
4. На основе RETURN POINT прочитать упомянутые файлы и спросить пользователя с чего продолжать (НЕ выбирать сам из OPEN — список может быть приоритезирован контекстом дня)

## Принципы

- **Указатели важнее пересказа** — `last_commit: SHA`, `file:line` вместо «я переписал функцию X»
- **OPEN может быть несколько** — не как handoff с LEFT=1
- **DEAD ENDS обязательно** при отвергнутых подходах
- **QUESTIONS обязательно** при открытых развилках
- **Никаких следующих промтов в буфере** — отличие от handoff
- **Никакого narration сессии** — факты, не сюжет
