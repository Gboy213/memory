# Memory Audit

Memory растёт линейно (~90 файлов уже), часть устарела, часть дублируется, часть противоречит. Без периодического cleanup'а MEMORY.md раздувается, шум в systemPrompt каждой сессии увеличивается.

Цель: найти и предложить пользователю что почистить. НЕ удалять автоматически — только показать список с обоснованием.

## Шаг 1: Inventory

Найди память — она живёт в одном из двух мест (или в обоих):
```bash
ls <repo>/memory/ 2>/dev/null                 # память в репо (пэк ставит сюда: <repo>/MEMORY.md + memory/)
ls ~/.claude/projects/*/memory/ 2>/dev/null   # локальная память Claude Code; папка проекта = путь к репо с дефисами
```
Инвентаризировать оба хранилища.

Прочитай:
- `MEMORY.md` — индекс
- Сначала `ls -la <memory>/*.md` чтобы видеть размеры и даты модификации
- Дальше выборочно: подозрительно большие, давно не модифицированные, или те что упоминаются в индексе с подозрительным описанием

Посчитай и сообщи:
- Сколько файлов всего по типам (feedback / project / reference / user)
- Размер MEMORY.md в строках
- 5 самых больших файлов
- 5 самых давно не модифицированных

## Шаг 2: Найти кандидатов на УДАЛЕНИЕ

**A. Устаревшие — упоминают то, чего больше нет:**

Для каждого подозрительного memory:
- Если упоминает путь к файлу — verify через `ls` что файл существует
- Если упоминает функцию/класс/SQL-таблицу — `grep -r` в проекте проверить наличие
- Если упоминает API endpoint — проверить в свежем коде что endpoint жив
- Если упоминает «делается через X» — проверить что X ещё используется

**B. Дублирует rules/<file>.md:**

Memory типа `feedback` часто бывают «слепком» правила. Если правило `rules/foo.md` уже говорит то же — memory избыточен (rules загружаются как глобальные инструкции).

Verify: прочитать соответствующий `rules/<topic>.md` и сравнить.

**C. Single-event память без повторений:**

Если memory создан после одного конкретного инцидента (например одна корректировка одного дня) и больше тема не возникала — кандидат на сокращение или удаление. Используй git log даты memory + поиск похожих корректировок в недавних транскриптах сессий.

## Шаг 3: Найти кандидатов на MERGE

Сравнивай memory попарно по:
- Триггерным словам (если два feedback'а реагируют на один и тот же сигнал)
- Тематической области (два про «правки Sheets», два про «деплой»)
- Структуре «Why / How to apply» — если совпадают почти дословно

Кандидаты на merge: два-три файла → один синтезированный, остальные удалить.

## Шаг 4: Найти ПРОТИВОРЕЧИЯ

Поищи пары memory где сказано противоположное:
- Одна «всегда X», другая «никогда X» — конфликт
- Одна «делай через A», другая «не используй A» — устаревшее vs актуальное
- Одна предписывает workflow Y, другая запрещает — нужно выбрать

Эти пары требуют решения пользователя — выноси отдельной секцией.

## Шаг 5: Отчёт пользователю

Структура отчёта (markdown, в чат):

```
## Memory audit (DATE)

Всего: N файлов · MEMORY.md M строк · по типам: feedback X / project Y / reference Z / user W

### 🗑️ Кандидаты на УДАЛЕНИЕ (X)
| Файл | Причина |
|---|---|
| feedback_foo.md | Упоминает удалённый файл bar.py |
| feedback_baz.md | Дублирует правило rules/coding.md |

### 🔀 Кандидаты на MERGE (Y пар)
| Файлы | Предлагаемый итог |
|---|---|
| feedback_a.md + feedback_b.md | Объединить в feedback_a_b.md, тема «X» |

### ⚠️ ПРОТИВОРЕЧИЯ (требуют решения)
| Файлы | Конфликт | Вопрос |
|---|---|---|
| feedback_x.md vs feedback_y.md | Одна говорит А, другая Б | Что сейчас актуально? |

### ✏️ Кандидаты на UPDATE
| Файл | Что обновить |
|---|---|
| feedback_z.md | Старый путь /old/path, новый /new/path |

### ✅ Без изменений (active)
N файлов используются активно, не трогать.
```

## Шаг 6: Применить решения пользователя

После approve'а:
1. Спросить ОДИН раз — «применяю X удалений, Y merge'ов, Z updates?» (НЕ AskUserQuestion, просто текст с подтверждением)
2. При «да» — выполнить:
   - Удалить файлы: `rm <memory>/<file>.md`
   - Merge: Write новый файл с объединённым контентом, удалить старые
   - Update: Edit указанных файлов
3. Обновить MEMORY.md:
   - Убрать строки удалённых
   - Добавить строки merged
   - Обновить строки updated
4. Финальный отчёт: «удалено N, merge'нуто M, обновлено K. Размер MEMORY.md был X строк, стал Y»

**НЕ удалять автоматически.** Только по явному approve пользователя на финальный список.

## Шаг 7: Bulk compression старых memory (опционально, по запросу)

Раз в 2-3 месяца — отдельный режим аудита для **сжатия старых memory** без удаления.

**Триггер:** пользователь говорит «сожми старые memory», «compression», «memory старше N месяцев сократи» или явно после long-term review.

**Кого сжимать:**
- Memory старше 60 дней по `stat -f "%Sm"`
- При этом БЕЗ обращений к файлу за последние 30 дней (см. ниже)
- Размер >2000 байт (мелкие уже сжаты)

**Как определить «без обращений»:**
- Грубо: дата последней модификации (`stat -f %m`) — если 30+ дней без правки, никто не редактировал
- Точнее: grep по transcripts последних 30 сессий — упоминался ли файл (`Read` на путь)

**Что сжимать (содержание):**
- Сохранить: frontmatter, основное правило, секция `**Why:**` (1-2 предложения), секция `**How to apply:**` (3-5 пунктов)
- Убрать: длинные примеры, повторяющиеся пояснения, цитаты из транскриптов, исторические даты «11.05.2026 такой-то баг», избыточный markdown
- Целевой размер: 800-1500 байт (с 3000-9000)

**Алгоритм:**
1. Для каждого кандидата — Read целиком
2. Идентифицировать что core (правило, why, apply) vs что декорация (примеры, история)
3. Переписать в сокращённую форму, сохранив core
4. **Перед перезаписью** — показать пользователю diff: «было N байт, станет M байт. Core сохранён? [показать новую версию]»
5. После approve — Write новой версии. Предусловие: память под git (репо) — перед перезаписью свежий коммит памяти; локальная память вне git — сначала скопировать папку (`cp -r … …-backup-<дата>`)

**НЕ сжимать:**
- Критичные для денег/методологии проекта — там длина оправдана нюансами
- Крупные feedback, где каждый описанный проход/итерация уникален — сжатие теряет нюансы
- Свежее 60 дней
- Любой `[[name]]`-target от других memory — переписка может сломать связи

**Эффект:** уменьшение systemPrompt-шума при сохранении знаний. На 60 файлах при средней компрессии 60% → экономия ~150 КБ памяти, но главное — каждое чтение memory становится быстрее, понимание чище.

**Безопасность:** откат — только через git-коммит памяти или копию папки, сделанные ДО перезаписи (см. предусловие в п.5).

## Что НЕ трогать

- Memory типа `user` (профиль) — это рабочий контекст
- Memory типа `project_*` без явного подтверждения пользователем — могут хранить уникальный контекст бизнеса
- Memory типа `reference` — обычно стабильны, проверять реже
- Свежие memory (моложе 7 дней) — пользователь только что зафиксировал, рано чистить
- Memory с `[[name]]`-ссылками от других файлов без проверки графа связей

## Принципы

- Лучше **предложить** удалить и не удалить, чем удалить лишнее
- Каждое предложение — с обоснованием (verify, цитата, ссылка)
- Не предлагать удаление memory, активно ссылающейся в `[[name]]` других memory или rules
- Если не уверен — оставь и пометь «требует ручного review»
